# BUI-621 local frontend draft

## Frontend release while submissions are pending

Production shows the invitation and then “Invites open soon” with an Email us link to sunny@buildingoro.ca. Header entry, the final invitation CTA/arrow, scrolling past the invitation, and all direct question hashes lead to the same notice. Production renders no form, receipt preview, or draft toolbar. Homepage CTAs point to this invitation.

The full form remains testable in local development and Vercel preview builds (`VERCEL_ENV=preview`). Other builds default to closed. This is a build-time distinction; URL parameters and browser storage cannot enable the form in production. Do not promote a preview artifact to production: rebuild for the production environment. Backend merges alone do not open intake; replace this temporary gate only after the frontend submission path has been connected and verified.

For the release, build normally and run `E2E_BASE_URL=<production-build-url> npm run e2e -- e2e/beta-availability.spec.js`. Those checks cover desktop/mobile, the final story transition, header entry, every direct question hash, reload, absence of fields/receipt controls, and no submission requests. The full `beta.spec.js` suite targets development or Vercel previews.

Based on OroLanding `main` at `21ab734`, using the installed `oro-kit` 0.1.0 foundations and components. The full BUI-621 description, its empty comment thread, related BUI-618, and backend PR #418 were read before implementation. #418 was still open.

Run `npm ci`, then `npm run dev -- --host 127.0.0.1 --port 4621 --strictPort`. Open http://127.0.0.1:4621/beta.

The draft uses the approved introduction with Sunny’s requested sentence removals, the same benefits and disclosures, all 12 question groups in order, native radio and checkbox controls, conditional answers, optional-answer clearing, independent consent values, validation and focus handling. Required defaults follow the ticket's working proposal. Text answers stay in React memory and disappear on reload; no applicant data is sent, logged, or written to browser storage. Analytics and cookie controls are disabled on this route.

Sunny's subsequent draft revision places all three consent checkboxes below the request button, checks all three by default, and uses the same support-size text as the review-response note. This supersedes the ticket's original unchecked defaults for this local draft; each checkbox can still be changed independently. The next revision removes the consent Optional labels, compacts their spacing, and moves the review-response sentence above the button. Only an unchecked Terms box disables the request button.

The invitation shows one of six pages at a time in a viewport-height stage. Wheel gestures, swipes, keyboard commands, and one centered forward arrow change pages with sequential fade-and-lift transitions. Trackpad momentum cannot skip through multiple pages. Longer content scrolls inside its page before advancing; reduced-motion preferences switch pages instantly. The extra opening examples, “iMessage beta” label, opening invitation tagline, and numbered chapter labels were removed at Sunny’s request, and the tester name is Oronauts throughout. Every invitation page types its headline and then its supporting text, replaying on each visit without blocking navigation. The revised vision and testing headlines follow Sunny’s copy; the accelerator page has been removed. Beta expectations are a checklist, the final sentence about using Oro again has been removed, and the perks use a compact centered vertical list with no supporting sublines. The separate gratitude page and Oro signoff have been removed. Reduced motion shows all text immediately. The page counter, progress marks, instructions, and visible back arrow have been removed. Scrolling forward from the final invitation page opens the form; scrolling back and keyboard navigation still revisit earlier pages. A persistent skip link opens a question-by-question journey: a name-only opening step, then the 12 original question groups followed by a dedicated invite-and-consent step. Each question is the page headline, with typing, a shared lavender/champagne background, a quiet progress line, a centered forward arrow, and a back control. Related contact fields and outfit-example answers stay together; the larger cards and section navigation are removed. The original question wording and softly animated choice pills remain. The phone helper sentence has been removed, and “Email us” links to sunny@buildingoro.ca. The name is required and retained in memory with the other answers. Question intent, answer values, optionality, dates, and the consent behavior are preserved. Back, next, and browser history preserve answers in memory. Each Continue validates its current step; final submission checks all steps and focuses the earliest invalid answer.

“Request an invite” validates the draft and reports that saving is not connected. The separate “Preview confirmation” control shows the proposed receipt with a visible preview label and preserves the form when returning. It is never represented as a saved application.
